## Remaining production hardening
- JS-readable auth cookies remain in the existing Bearer architecture. They now use Secure on HTTPS, SameSite and short lifetime; a complete HttpOnly session/BFF migration is still needed for stronger XSS resistance.
- Per-process quotas/rate limits are bounded, but not shared between replicas. Use a shared limiter before scaling.
- AI cannot execute tools, but model answer correctness and harmful/off-topic response handling require live red-team evaluation. Prompt filters are not a guarantee.
- Student completion percentage remains the legacy stub; history is persistent, but no per-lesson progress tracking is claimed.
- Existing PayPal checkout sells courses to one merchant only. Seller-specific disbursement and 2% platform commission are not implemented. The recommended multiparty partner-onboarding architecture and approval/fee/refund requirements are documented in `docs/environment-setup.md`; no teacher or buyer API secrets should be collected.
- Realtime channels are deliberately disabled to prevent private row broadcasts; REST refresh works. Background doubt email needs a separate retry-safe flow; password/OTP sender now defaults to Resend HTTPS.
- Legacy destructive CRUD and existing-data edge cases need staged live regression checks. Whole-project coverage was not measured; 80% coverage is not claimed.
- Review mutation field bounds and legacy raw-error logging still need dedicated hardening; the current positive local review checks are not an exhaustive malformed-input audit. Teacher profile editing and admin/destructive flows are not comprehensively proven by the new auth/profile tests.
- Email delivery and database commit cannot be atomic; a database failure after mail delivery can leave an emailed code unusable. Requesting a new code remains available after recovery; a durable outbox would improve this further. Timeout is an uncertain send result and is not automatically retried.
- `capture_unknown` recovers only from a matching completed PayPal order read. `refund_unknown` blocks another automated refund and preserves access until manual provider/database reconciliation. PostgreSQL lock/rollback guarantees still need live verification; controller tests use mocks.
